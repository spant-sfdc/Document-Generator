1 Introduction

Every Salesforce implementation reaches the same inflection point — the moment a stakeholder asks: "Can we just generate a document from this record?" And suddenly what feels like a simple request turns into a conversation about template engines, middleware, third-party licences, and custom Apex.

What you're about to see is a different approach. DocGen is a fully Salesforce-native document generation framework — built from the ground up with a metadata-driven architecture. No middleware. No external dependencies. No hardcoded mappings.

It solves three specific problems that have frustrated teams for years. First — rigid templates that break the moment a field name changes. Second — relationship resolution that requires a developer every time you need parent or child data in a document. And third — PDF generation that either relies on legacy Visualforce or sends your data to an external service.

DocGen replaces all of that with a guided wizard, a dynamic token engine, and a centralised PDF renderer — all inside Salesforce. Let's walk through it.

2 Business Scenario — Story Setup

Our story starts with a Development Director at a nonprofit organisation. Her name is Priya. Priya manages major gift campaigns and is preparing a formal donation proposal for Robert Thomas — a high-value donor who has committed to a $71,000 major gift to the Education Support Fund.

The proposal needs to pull donor information from the Account, include a breakdown of the donation line items, and — because this is a major gift above the organisation's threshold — display a dedicated acknowledgement section reserved exclusively for top-tier contributors.

Priya's team used to do this manually. A staff member would open Word, copy data from Salesforce, and paste it field by field. Every document took twenty minutes and carried the risk of stale data. Today, Priya does it in under two minutes, directly from Salesforce — and the document is automatically attached to the record the moment it is generated.

Let's see exactly how that works — starting with how an admin sets up the template.

3 Admin Configuration Flow
STEP A Upload Template

The first thing an admin does is upload the document template. Templates are written in HTML — a format that any designer, developer, or technically-minded admin can work with. It gives you full control over layout, typography, tables, and conditional sections without the constraints of a drag-and-drop builder.

The template uses a simple double-curly-brace syntax for placeholders — tokens like {{donor_name}}, {{donation_amount}}, or {{campaign_title}}. Crucially, these token names are completely free-form. You name them whatever makes sense to your team. There is no dependency on Salesforce field API names here.

The moment the file is uploaded, the wizard scans it and extracts every token automatically. No manual registration required.

STEP B Object Selection

Next, we tell the wizard which Salesforce objects this document pulls data from. The primary object is the record we're generating from — in this case, the Opportunity. From there we can add parent objects, traversed via relationship, and child objects from related lists.

For this proposal, we need three objects. The Opportunity as our primary. The Account — Robert Thomas's donor record — as our parent. And Opportunity Line Items as our child object, which will populate the donation line item table.

What makes this powerful is that the relationship resolution happens dynamically at generation time. The system traverses standard and custom lookups automatically. You don't hardcode a relationship path or write a SOQL join — you just declare the object, and the engine handles the rest.

  1. Click Next: Select Objects

  4. [1 sec pause]

STEP C Token Mapping — Move slowly here

This is the core of what makes DocGen different — the mapping screen. Every token that was extracted from the template appears here as a row. And for each one, we define exactly where its value comes from.

Notice how the token names — {{donor_name}}, {{donation_amount}}, {{campaign_title}} — are written in plain language, not Salesforce API names. That's intentional. The mapping is the bridge between your human-readable template and the Salesforce data model. You control both sides independently.

For {{donor_name}}, we map it to the Account's Name field — traversing the parent relationship from the Opportunity. For {{donation_amount}}, we map it to Opportunity Amount, and we can apply a format override to render it as a currency string — dollar sign, two decimal places, all automatic.

For the repeating line items section — everything inside the {{#line_items}} block — we map each token to its corresponding OpportunityLineItem field. Contribution type, quantity, unit price, total price. The engine will iterate over every child record and render one row per item.

There is also a Demo Mode auto-fill here — for environments where the scenario is pre-configured. One click populates the entire mapping table instantly. In production, an admin builds this once and never touches it again.

STEP D Variables — Conditional Logic

The variables screen is where business logic enters the document. Any {{#if variableName}} block in the template gets listed here automatically. An admin defines what that variable evaluates to — a boolean comparison, a static value, or a date expression.

For Robert Thomas's proposal, we have one variable: isMajorDonor. The expression is straightforward — if the mapped donation amount is greater than ten thousand dollars, the condition is true, and a major donor acknowledgement section appears in the document. If the amount is below that threshold, the section is invisible. Same template, different output based on live record data.

An admin can change this threshold, rename the variable, or add new conditions entirely — without touching a line of code. The logic lives in metadata.

  1. Click Next: Variables

  3. Click Auto Fill Variables

  5. Hover slowly over the expression field — let viewer read it
  6. [2 sec pause — this is a key differentiator moment]

7 Template Edit & Maintenance Flow

One of the most underestimated capabilities of this platform is how easy it is to maintain. If the organisation changes its threshold for major donor status from $10,000 to $25,000 — that's a five-second variable edit. If the legal team updates the language in a conditional section — the HTML template file is updated and re-uploaded. If a new field needs to appear in the document — a new mapping row is added.

No Apex changes. No deployment cycle. No developer ticket. The entire configuration surface is owned by the admin team, and every change takes effect immediately.

This is the architecture advantage that compounds over time. The first implementation is the hardest part. Every iteration after that is minutes, not days.

8 Outro — Vision, Maturity, Advantage
PART A Future Roadmap

What you've seen today is the production-ready foundation. And the roadmap extends it significantly. We are building OCR ingestion — the ability to upload a scanned PDF or image of an existing document and extract its structure automatically. AI-assisted field mapping, where the system analyses your template tokens and suggests the most probable Salesforce field for each one. Intelligent recommendations that learn from prior configurations across templates. And automated data extraction from legacy document archives.

The architecture is designed for exactly this expansion — each capability is a new service layer, not a rewrite.

PART B Production Maturity

The platform is production-ready today. The PDF engine is centralised and consistent — the same renderer is used regardless of the template or object. The architecture is metadata-driven end to end — every configuration is stored in Salesforce and deployable via standard metadata API. Field Level Security is enforced on every query. And the entire system is contained within Salesforce — no external API calls, no data leaving the platform.

PART C Competitive Advantage

Traditional document generation in Salesforce falls into one of two categories. Either it requires a third-party tool with a separate licence, data leaving Salesforce, and an integration to maintain. Or it requires custom Apex, hardcoded SOQL, and a developer every time something changes.

DocGen is neither. It is Salesforce-native, meaning no external dependency and no data transfer. It is fully configurable by admins, meaning no developer cycle for template changes. Its token engine is free-form, meaning templates can be written by designers without knowledge of the Salesforce data model. And its PDF generation is server-side and consistent, meaning no rendering differences between users or browsers.

For organisations that generate documents at scale — proposals, receipts, agreements, reports — this is the architecture that makes that sustainable. One implementation. Unlimited templates. Zero ongoing developer dependency.
