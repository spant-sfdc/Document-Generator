1. Architecture Overview

DocGen is a pure Salesforce-native platform built on LWC + Apex. There are no managed packages, no external services, and no per-document API calls. All logic — template parsing, data resolution, merge, and PDF rendering — runs inside the Salesforce org.

Key design principles

  • Metadata-driven — template configs (mappings, variables) are stored as JSON on ContentVersion records; no custom SObjects required for template state.
  • Security-first — every SOQL uses WITH SECURITY_ENFORCED; schema operations check isAccessible() on every field before including it in a query.
  • Auto-resolve first, manual override — the SmartTokenResolver auto-matches tokens to fields so admins don't need to map everything manually. Explicit mappings always take priority over auto-resolved ones.
  • Renderer agnostic — the merge engine produces clean HTML; the VF PDF renderer consumes it. Swapping the renderer requires only changing DocGen_FileService.

2. Request Lifecycle — Document Generation

When an end user clicks Generate Document, the following sequence executes in a single synchronous Apex transaction:

  1. LWC calls DocGen_Controller.generateDocument(recordId, templateRecordId)
    The controller is the single entry point for generation. It loads the template config JSON from the ContentVersion record.
  2. Variable resolution — DocGen_VariableResolverService.resolveWithData()
    System variables (today, currentUser, orgName, EIN, etc.) are resolved first. EXPRESSION-type variables are evaluated against the primary record data loaded in the next step.
  3. Data resolution — DocGen_DataResolverService.resolveData()
    Groups all field mappings by object. Executes one SOQL per object (primary + each unique child). Flattens SObject results into Map<String, Object> for the merge engine. Parent traversal fields are included in the primary SOQL as dot-notation paths (e.g. Account.Name).
  4. Template merge — DocGen_MergeEngineService.mergeTemplate()
    • Injects resolved variable values
    • Expands repeating child sections ({{#RelName}}...{{/RelName}})
    • Evaluates conditional blocks ({{#if var}}...{{/if}})
    • Replaces all primary field tokens with their resolved values
    • Applies format overrides (currency, date, upper, lower, number)
  5. PDF rendering — DocGen_FileService → VF page
    The merged HTML is passed to DocGen_PdfRenderer (a Visualforce page with renderAs="pdf"). The VF page HTML viewer renders the document and the binary PDF blob is captured.
  6. File save — DocGen_FileService.saveDocument()
    The PDF blob is saved as a new ContentVersion and linked to the originating record via ContentDocumentLink. The ContentDocumentId is returned to the LWC for the download link.

3. Smart Token Resolver — DocGen_SmartTokenResolver

The SmartTokenResolver parses HTML template content and automatically produces TokenMappingWrapper objects for every unmapped {{token}} it can resolve against the primary object's schema.

Public API

MethodPurpose
mergeWithAutoResolved(primaryObject, templateHtml, explicitMappings)Merges auto-resolved mappings with an existing explicit list. Explicit mappings take priority — tokens already covered are skipped.
resolve(primaryObject, templateHtml, skipKeys)Pure auto-resolve — produces a mapping list from scratch. Throws DocGen_Exception for tokens that cannot be resolved.

Token parsing logic

The parser uses a regex \\{\\{([^{}]+)\\}\\} to extract all tokens and a section stack to track which tokens are inside child relationship blocks:

  • {{#RelName}} — pushes RelName onto the section stack; emits a child section mapping
  • {{/RelName}} — pops the stack; no mapping emitted
  • {{#if ...}} — pushed to stack but treated as a directive, not a child relationship
  • {{sys.*}} — skipped entirely (handled by VariableResolverService)
  • All other tokens — resolved based on current stack context

Resolution dispatch

Token patternResolution path
{{FieldName}} (no dot, not in section)Direct primary field lookup via primaryFieldMap
{{Rel.FieldName}} (contains dot)Parent traversal — validates relationship name + final field via describe; sets relationshipPath
{{#SectionName}}Child section — looks up childRelNameToObj; sets isRepeating=true, repeatObject=childSObjectApiName
{{FieldName}} inside a sectionChild field — looks up childFieldMaps[childObj]; sets isRepeating=true, repeatObject=childObj
Context key deduplication The resolver uses context keys in the format "childObj|{{token}}" or "__primary__|{{token}}" to avoid emitting duplicate mappings when the same token appears multiple times in the template.

Schema model (ObjSchema)

Built once per resolve call via Schema.getGlobalDescribe(). Contains:

  • primaryFieldMap — lowercase field name → API field name (primary object only)
  • relNameToRefObject — lowercase relationship name → referenced SObject API name (for parent traversal)
  • childRelNameToObj — lowercase child relationship name → child SObject API name
  • childFieldMaps — child SObject API name → (lowercase → API field name)

4. Merge Engine — DocGen_MergeEngineService

The merge engine takes the resolved data maps and the template HTML and produces the final merged HTML in a single pass. It processes content in a strict order to ensure correctness.

Merge order

  1. Variable injection — all {{varName}} and {{sys.varName}} tokens replaced with their resolved values from resolvedVariables map.
  2. Repeating section expansion — child sections detected with regex \\{\\{#([a-zA-Z0-9_]+)\\}\\}([\\s\\S]*?)\\{\\{/\\1\\}\\}. For each section, getSectionMappings() retrieves the child field mappings; the row template is cloned and field-merged once per child record.
  3. Conditional block evaluation — {{#if varName}}...{{/if}} blocks evaluated against a combined data map (primary fields + resolved variables). Block is retained if the variable is truthy, removed if falsy.
  4. Primary field replacement — all non-repeating token mappings iterated; each token replaced with the value extracted from primaryData via sourceField or relationshipPath. Format override applied if set.

Format override implementation

applyFormat(rawValue, formatOverride) parses the override as type:param:

if (fType == 'currency')  → '$' + Decimal.valueOf(rawValue).setScale(2)
if (fType == 'date')      → Datetime.format(fParam)   // e.g. 'MM/dd/yyyy'
if (fType == 'number')    → Decimal.setScale(Integer.valueOf(fParam))
if (fType == 'upper')     → rawValue.toUpperCase()
if (fType == 'lower')     → rawValue.toLowerCase()

Child section field resolution — getSectionMappings()

The method resolves the effective child SObject API name by looking up the section's structural marker (the {{#RelName}} token with no sourceField). It then collects field mappings using two strategies:

  • Primary: isRepeating == true AND repeatObject == effectiveObj
  • Fallback: sourceObject == effectiveObj (handles mappings with blank repeatObject)

Truthiness evaluation

isTruthy(Object val): returns false for null, Boolean false, string "false", string "0", empty string, or string "null". Returns true for everything else including Boolean true and any non-empty, non-zero string.

Expression evaluation

evaluateExpression(expr, data) splits the expression string on the first operator found (tried in order: >=, <=, !=, ==, >, <). Left-hand side is used as a key to look up a value in the primary data map. Right-hand side is compared numerically if both sides parse as Decimal, or as strings otherwise. The special value null on the right-hand side is supported for == and != only.

Expression evaluation order dependency resolveWithData() receives the primary data map from DataResolverService, which is populated first. EXPRESSION variables cannot reference other variables — only primary object field values.

6. Data Resolver — DocGen_DataResolverService

Responsible for converting the token mapping list into live Salesforce data. Executes one SOQL query per unique object (primary + each child SObject), then flattens results into Map<String, Object> for the merge engine.

SOQL construction strategy

  • Groups mappings by object using groupFieldsByObject().
  • Parent traversal fields (those with a relationshipPath) are added to the primary object's SOQL as dot-notation paths, e.g. SELECT Account.Name, Account.BillingCity FROM Opportunity WHERE Id = :recordId.
  • Child object SOQLs are built dynamically: SELECT [fields] FROM [childObj] WHERE [lookupField] = :recordId WITH SECURITY_ENFORCED LIMIT [maxRows].
  • The parent lookup field is discovered at runtime via getParentLookupField(), which iterates all REFERENCE fields on the child SObject to find one that references the parent object.

Field validation — buildFieldList()

Before including any field in a SOQL query, buildFieldList() checks:

  • For simple fields: field exists in Schema.getGlobalDescribe() field map AND isAccessible() == true
  • For traversal paths: validateTraversalPath() walks each relationship segment by matching getRelationshipName() (not the field API name) and confirms the final field is accessible

Record flattening — flattenRecord()

Uses SObject.getPopulatedFieldsAsMap() (not SObject.get()) to avoid SObjectException: Invalid field on relationship keys. Nested SObject values (parent traversals returned by SOQL) are recursively flattened with dot-notation keys, e.g. {"Account.Name": "Robert Thomas Foundation"}.

Child section key

Child results are stored in childRecords keyed by the section name as used in the template (e.g. "OpportunityLineItems"), not by the SObject API name. This allows the merge engine to look up child data using the same relationship name from the template token.

7. Parent / Child Resolution Implementation

Parent traversal path handling

A parent traversal token ({{Account.Name}}) flows through the system as follows:

  1. SmartTokenResolver: detects the dot, splits on first dot, looks up the relationship name in relNameToRefObject, validates the final field on the referenced object, then sets m.relationshipPath = "Account.Name".
  2. DataResolverService: adds "Account.Name" to the primary object's field list. Generates SOQL: SELECT Account.Name FROM Opportunity WHERE Id = :recordId.
  3. flattenRecord(): the SOQL result contains a nested Account SObject. Flattening produces {"Account.Name": "Robert Thomas Foundation"}.
  4. MergeEngineService.extractValueFromData(): uses mapping.relationshipPath as the key to look up "Account.Name" in the flat data map.

Child repeating section handling

  1. Template: {{#OpportunityLineItems}}...{{/OpportunityLineItems}}
  2. SmartTokenResolver: emits a structural marker mapping (token="{{#OpportunityLineItems}}", repeatObject="OpportunityLineItem", sourceField=null).
  3. DataResolverService: detects isRepeating=true, executes SELECT [fields] FROM OpportunityLineItem WHERE OpportunityId = :recordId, stores result as childRecords["OpportunityLineItems"].
  4. MergeEngineService.processRepeatingSections(): matches the section name, retrieves rows, clones the row template, merges each row's field values, concatenates all rows, replaces the full {{#...}}...{{/...}} block with the expanded HTML.
Section name vs SObject API name The template uses the child relationship name (OpportunityLineItems) but the child SObject API name is OpportunityLineItem (singular). The structural marker's repeatObject field bridges this distinction. getSectionMappings() resolves the effective SObject name from the marker before collecting field mappings.

10. Deployment Notes

Full deployment (first-time)

# Deploy all DocGen components
sf project deploy start --manifest manifest/docgen-package.xml --target-org <alias>

# If custom fields fail due to PermissionSet dependency, deploy fields first
sf project deploy start --manifest manifest/docgen-fields-only.xml --target-org <alias>
sf project deploy start --manifest manifest/docgen-package.xml --target-org <alias>

Package manifest contents (docgen-package.xml)

  • 13 Apex classes (DocGen_*)
  • 13 LWC components (docGen*)
  • 2 Custom Metadata Types (DocGen_Config__mdt, Demo_Mode__mdt)
  • 1 Custom Metadata record (DocGen_Config__mdt.Default)
  • 6 Custom Objects / Platform Events (DocGenerationBatchProcess, DocGenerationQueryResult, DocumentGenerationProcess fields)
  • 7 Custom Fields (across Account, Opportunity, OpportunityLineItem)
  • 2 Permission Sets (DocGen_Full_Access, DocGen_Demo_Fields)
  • 2 Visualforce Pages (DocGen_PdfRenderer, DocGen_HtmlViewer)
  • 1 Custom Tab (DocGen_Wizard)
  • 1 Custom App (DocGen_Document_Generator)
  • 2 FlexiPages (DocGen_Template_Builder_Home, DocGen_Wizard_Page)

Post-deployment setup checklist

  1. Assign DocGen_Full_Access to all DocGen users via Setup → Permission Sets
  2. Assign DocGen_Demo_Fields to demo / admin users
  3. Open DocGen_Config__mdt in Setup → Custom Metadata Types → Manage Records and populate Org_Display_Name__c, Org_EIN__c, Org_Address__c, Org_Phone__c, and Org_Website__c
  4. Add the DocGen_Wizard_Page or DocGen_Template_Builder_Home flexipage to the relevant Lightning App pages via App Builder
  5. Add the docGenRecordAction LWC component to the record page layout of your primary object(s) via Lightning App Builder
  6. Run the demo data Apex script (scripts/create-demo-records-foundation.apex) in the target org to create the Robert Thomas Foundation scenario

11. Security Model

SOQL security

All dynamic SOQL queries in DocGen_DataResolverService use WITH SECURITY_ENFORCED. If any field in the SELECT clause is inaccessible to the running user, Salesforce throws a System.QueryException — DocGen surfaces this as a user-visible error rather than silently omitting the field.

Schema validation (SOQL injection guard)

DocGen_SchemaService.validateObjectName() is called before every dynamic SOQL construction. It verifies the supplied object name exists in Schema.getGlobalDescribe(). This prevents SOQL injection via crafted object name strings passed from the LWC.

Field-level security

buildFieldList() checks isAccessible() on every field before including it in a query. Fields that fail the check are silently excluded from the field list rather than throwing, to prevent template generation from failing when a user lacks access to optional fields.

Sharing model

All Apex classes use with sharing except DocGen_MergeEngineService (pure string manipulation, no data access) and DocGen_Wrappers (data transfer objects only). Record-level sharing rules are therefore enforced for all data reads.

ContentVersion access

Template HTML files and generated PDFs are stored as Salesforce Files (ContentVersion). Access is governed by standard Salesforce file sharing — the running user must have access to the record the file is linked to. DocGen_Full_Access grants the Create permission on ContentVersion needed to upload templates and save generated PDFs.

12. Extension Points

Adding a new variable type

  1. Add a new when branch in DocGen_VariableResolverService.resolve() for the new type string.
  2. Add the type option to the docGenVariablesPanel LWC type picklist.
  3. If the type requires runtime data (like EXPRESSION), handle it in resolveWithData() instead of resolve().

Adding a new format override

Add a new if (fType == '...') branch in DocGen_MergeEngineService.applyFormat(). No other changes are needed — the format string is stored in the mapping config and applied at merge time.

Replacing the PDF renderer

All PDF rendering is isolated in DocGen_FileService and the two VF pages. To replace the Visualforce renderer (e.g. with a third-party API), modify only DocGen_FileService. The merge engine, token resolver, and data resolver are completely decoupled from the rendering mechanism.

Supporting multi-hop parent traversal

Currently, DocGen_SmartTokenResolver.resolveParentTraversal() handles single-hop only (one dot in the token, e.g. {{Account.Name}}). Multi-hop (e.g. {{Account.Owner.Name}}) would require extending validateTraversalPath() in DocGen_DataResolverService and the field list builder to support deeper relationship paths.

Demo Mode extension

The Demo_Mode__mdt CMT allows pre-seeding a wizard session with a complete set of mappings and variables. To add a new scenario, create a new CMT record with Is_Enabled__c = true (only one record should be enabled at a time) and populate Auto_Mapping_JSON__c and Auto_Variables_JSON__c with serialised JSON matching the wrapper schemas.
